## Причина отказа

`confirmApplicability()` раньше проверял только append-only ApplicabilityConfirmation.
Даже при точной цитате и корректном JSON любому N/A требовалась положительная запись
по conversationId + checklistId + criterionKey. Для допустимой навигации не было
автоматического независимого способа подтвердить условие. Поэтому 03 отклонялся с
502 AI_NA_UNCONFIRMED до транзакции создания Evaluation; отсутствие оценки ожидаемо.
Путь вызова и условие блокировки подтверждены кодом и регрессией. Исторический JSON
ошибки/ответа не предоставлен, поэтому остальные решения Gemini не подтверждаются.

## Исправление и границы

Добавлен `src/modules/evaluations/identity-applicability.js`. Он подтверждает только
проверяемый класс публичных RU-инструкций самостоятельного поиска отчёта/тарифа:

- Применяется к исходной точной формулировке 03: boolean, allowNa=true, то же описание
  и naCondition. Не переносится на изменённый критерий или recording_start_missing.
- Проверяет весь исходный транскрипт, а не выбранную AI цитату/диапазон; externalId,
  na_reason, уверенность AI и утверждение об авторизации не дают разрешение.
- Каждая содержательная реплика должна целиком соответствовать известной инструкции,
  навигационному запросу или допустимому продолжению. Нужны и запрос, и инструкция;
  одних приветствий/прощаний недостаточно. Правило работает и для другого ID/короткого
  самостоятельного примера, не привязано к p1-ru-027.
- Бот допускается только как известная общая заставка/перевод на оператора; это не
  факт идентификации. Неизвестные роли/системные события и дополнительные поля реплики
  оставляют случай неподтверждённым.
- Запросы баланса, переводов, смены данных, отправки личного отчёта, персональные
  значения/идентификаторы/ссылки, противоречивые и неизвестные формулировки автоматически
  не разрешаются. В частности, одного «Какой у меня тариф?» без проверенного контекста
  навигации недостаточно.

Это консервативный набор полных шаблонов, **не универсальный семантический классификатор**.
Другие RU-формулировки, KZ/EN и новые критерии сохраняют прежний путь независимой
проверки/доверенного факта. Существующая поддержка языков/обычных оценок не менялась.
Шаблоны нельзя расширять одним ключевым словом или на основании одной причины AI.

Общий `confirmApplicability()` объединяет это правило и прежние доверенные факты.
Отдельный `confirmRecordedApplicability()` оставляет CLI `na:confirm` строгую проверку
именно записываемого факта: автоматическая классификация не оправдывает неверный rule.
Миграция/новый публичный endpoint/запись ручного подтверждения не нужны.
Исходные transcript/timestamp/channel/ID и AI-объяснения не переписываются.

## Техническая проверка и смысл — разные этапы

1. Backend проверяет JSON, UUID/версию, полный набор критериев и типы.
2. Проверяет точные цитаты, turnIndex, включительные границы checked_range.
3. Для N/A проверяет answer=null, непустую причину и независимую применимость.
4. Только после успешных проверок вызывает существующий calculateScore и атомарно
   сохраняет Evaluation/результаты. Новая политика не обходит первые два этапа.

Синтетическая неправильная цитата для самого p1-ru-027 по-прежнему даёт
502 AI_INVALID_EVIDENCE. Технически корректная цитата при защищённом/неоднозначном
запросе даёт 502 AI_NA_UNCONFIRMED и не оставляет частичную Evaluation.
Грубая ошибка, правила приветствия v1/v2, веса и формула scoring не меняются.

## Если другой N/A не подтверждён

Безопасный отказ сохраняется. Не превращать N/A в false/true автоматически и не запускать
платный повтор по таймеру. Корректный процесс повторной проверки:

1. При наличии сохранённого исходного JSON проверить его офлайн на тех же UUID,
   версии и неизменённом транскрипте. Сохранить исходник, не редактировать успешные оценки.
2. Для неизвестного контекста выполнить доверенную проверку применимости. Если действие
   требовало идентификации, подтвердить обычный ответ по доказательствам, а не выдавать N/A.
3. Ошибку AI передать AI-разработчику с безопасными диагностическими данными. В будущем
   отклонённый JSON можно сохранять как отдельный защищённый артефакт попытки, не как
   успешную Evaluation; такое хранилище в этом исправлении не добавлялось.
4. Только явно одобренный новый запрос может снова вызвать Gemini. Не применять
   Appeals API к ещё не существующей Evaluation и не считать отсутствие записи нулём.

## Обновление Docker / PowerShell


Сначала убедитесь, что существующие PostgreSQL/AI сервисы запущены. Пересобирается только
Backend; .env, AI, volumes и оценки не удаляются. Новых миграций нет, восьмая схема
остаётся актуальной. Для локальной проверки на **отдельной** подготовленной тестовой БД:

