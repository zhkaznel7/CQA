## Совместимость

- POST /v1/evaluations и формат conversation_id/checklist_id/checklist_version/results
  не изменены. Поля criterion_id, answer, na, na_reason, explanation, evidence,
  checked_range остаются прежними. condition_id — только внутреннее поле Gemini.
- Backend уже требует диапазон при boolean=false (`AI_MISSING_RANGE`), поэтому AI
  теперь отклоняет тот же некорректный результат раньше. Никаких выдуманных границ.
  При HTTP-отказе AI Backend использует существующее 502 AI_HTTP_ERROR, не пересчитывает
  некорректный результат. Это существующая обработка upstream-ошибки.
- Проверяются включительные границы, точные цитаты, turnIndex и попадание evidence
  внутрь checked_range. Индексация API остаётся от 0, evidence_turns экспорта — от 1.
- Boolean=true, N/A и числовой 0 не становятся отрицательным boolean. Отдельное правило
  omission сохраняется; flag=false в Gemini по-прежнему требует проверки всего диалога.
- N/A не разрешается автоматически: Backend требует allowNa и независимый факт для
  конкретного диалога/версии. Исключение обрезанного звонка и запрет чатов не изменены.
- Баллы считает существующий Backend calculateScore; формулы/веса/grossError не менялись.
  AI-export продолжает принимать --scores, а официальным источником итогов остаётся
  Backend CLI. Изменение не объединяет два экспортёра и не переносит scoring в AI.
- Новые compare/export проверки превращают ранее некорректный отрицательный boolean
  без диапазона в unavailable/error. Это намеренное ужесточение, не изменение шкал
  или автоматическая перезапись сохранённых оценок.

## Безопасность и квота Gemini

В diff нет новых provider-вызовов, retry-циклов, сетевых адресов, ключей или логирования

сохранённых успешных и ошибочных ответов.

хостам. Gemini-тесты подставляли ответы через request; Python-контейнеры запускались
с --network none. CLI Gemini-server, --check, --check-fixture и реальные ключи не
использовались; запросов Google не было.

Риски, которые офлайн-проверка не снимает:

1. Принятие новой nullable-схемы реальным Gemini и качество выдачи требуют отдельного
   согласованного вызова. В этом PR нельзя заявлять проверенный реальный прогон 65 DEV.
2. Новый prompt/fingerprint требует нового каталога для следующего разрешённого прогона.
   Старые manifest/ответы не следует заменять или обходить, автоматического повтора нет.
3. Более строгая проверка может увеличить число INVALID_MODEL_OUTPUT для ответов без
   диапазона. Дополнительный платный повтор сам по себе не запускается; его нужно
   отдельно согласовывать. Отсутствующие данные не заменяются успешной оценкой.
4. Для полного штатного Node→Python теста нужен Python 3. AI-разработчику стоит улучшить
   диагностическое сообщение subprocess-теста, чтобы ошибка Python не скрывалась assert.
