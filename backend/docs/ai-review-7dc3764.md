Публичный контракт остался прежним: `POST /v1/evaluations`, стандартный порт 8001, JSON с `conversation_id`, `checklist_id`, `checklist_version`, `results`; для каждого критерия — `criterion_id`, `answer`, `na`, `na_reason`, `explanation`, `evidence`, `checked_range`.

Обновлённый кандидат не меняет `http.mjs`, mock-сервер и его фикстуры. Backend-тесты фактически запускают командный HTTP mock. Поддержка RU/KZ/EN, динамических ключей и версий, boolean/scale/flag, voice call/voice/call, строгих цитат, индексов и диапазонов прошла соответствующие тесты.

Дополнительно выполнено шесть сценариев через настоящий локальный HTTP Backend → кандидатный `evaluateGemini()`. Вместо Google внедрён синтетический провайдер через предусмотренную зависимость `request`; оболочка HTTP возвращала согласованный JSON. Использованы свободные локальные порты, без вмешательства в работающий AI на 8001. Это проверка адаптера и интеграции, не смыслового качества Gemini.

Полный Backend-набор включает проверки PostgreSQL, scoring, групп, версий, идемпотентности, конкурентных запросов и решений по апелляциям, отката транзакций, экспорта и неизменности исходных AI-результатов.

## Что изменилось в AI и совместимость

1. Provider JSON Schema упрощена: отдельного nullable `condition_id` больше нет. Используется строка `checks.condition` со стабильным ID либо точным официальным текстом условия. Неизвестные условия, дубликаты и пропущенные условия отклоняются; произвольного нечёткого сопоставления нет. Это внутренний формат Gemini, Backend его не получает.
2. Раздельно проверяются обязательные части приветствия, выявления потребности, эмпатии, завершения и грубых нарушений. Положительное приветствие требует доказательства из первого ответа оператора, а не бота. Для boolean=false обязателен `checked_range`; false-флаг и числовой ноль не путаются с boolean=false.
3. Для 02 отдельно проверяется достаточность исходной информации; уход клиента не заменяет это условие. Для 04 добавлена инструкция об уходе до формулировки вопроса, с учётом ранее переданного боту контекста. N/A не разрешается только на основании `allowNa`.
4. Некорректный вспомогательный `review` даёт диагностическое предупреждение; критериальные ответы, цитаты, диапазоны и типы продолжают проверяться строго. `review` не входит в Backend-контракт.
5. В сервере и CLI согласован default model: `gemini-3.5-flash-lite`, prompt `2.4.3`. Явный `GEMINI_MODEL` сохраняет приоритет. Это изменение выбора модели следует учитывать при будущем разрешённом платном запуске.
6. Диагностика сохраняет приватное тело ответа провайдера с маскированием ключа, без перезаписи существующего артефакта. Ошибка локальной записи диагностики не превращает HTTP 400 в сетевую ошибку с повтором. Артефакты могут содержать данные диалогов: хранить только в приватной игнорируемой директории запуска.
7. Batch-runner сохраняет маркеры и результаты, учитывает закэшированный `GEMINI_REQUEST_REJECTED` и прекращает дальнейшие обращения; автоматического повтора платных запросов нет. Replay архива проверяет fingerprint/manifest и не перезаписывает исходный архив.
8. Python-экспортёр получает готовый score из Backend через `--scores`, дополнительно проверяет оболочку источника, доказательства и диапазоны. Существующий output не заменяется без `--overwrite`. Основным механизмом официального экспорта остаётся Backend, как источник сохранённых баллов и версий.

Подтверждённых новых нарушений публичного контракта, формулы Scoring Engine, сохранения апелляций или официального JSON 1.0 не найдено. Исторический `ai/evaluation/audit-2026-11-08.json` относится к старым версиям и не является результатом этой проверки.

## Ограничения и готовность к PR

- Исправление реального `400 INVALID_ARGUMENT` **не подтверждено запросом к Google**: пройдены офлайн-тесты структуры Schema и обработки ошибок. Приём новой схемы конкретной моделью, её доступность и качество ответов остаются непроверенными. Для проверки потребуется отдельное разрешение на платный вызов.
- Для N/A 02 и 04 Backend по-прежнему требует независимое подтверждение. Синтетический HTTP-тест воспроизвёл отказ без него и успех после него. Это существующая защита, а не новая ошибка JSON-контракта. Для полностью автоматического Gemini-прогона необходимо согласовать источник доверенных фактов; нельзя просто принимать любой N/A модели.
- Новая инструкция AI для 04 сама по себе не устраняет `AI_NA_UNCONFIRMED`. Если требование PR — запуск всех DEV-диалогов через Gemini без дополнительных подтверждений, такое требование пока не выполнено.
- Зелёные офлайн-тесты не означают проверки новых реальных ответов Gemini, всех 65 DEV-диалогов через Gemini или готового официального набора результатов.
- Окончательный Docker-прогон совместной сборки после объединения не выполнялся в рамках этой проверки.

**Заключение:** кандидат готов к PR и объединению для существующей mock/офлайн-интеграции: конфликтов по изменяемым путям и регрессий в выполненных тестах нет. Готовность полноценного Gemini-сценария остаётся условной по указанным двум вопросам — приём схемы Google и доверенное подтверждение N/A. Merge, commit и push не выполнялись; изменений производственного кода не потребовалось.
