# CQA AI service

AI оценивает оператора по снимку чек-листа из Backend: ответы, объяснения и доказательства.
Баллы и PostgreSQL относятся к Backend. Внешний контракт сохранён: POST /v1/evaluations,
порт 8001, criterion_id равен criteria[].key. Индексы реплик от нуля, checked_range включителен.

## Запуск

Node.js 20+, npm-зависимостей у AI нет. Запуск из корня проекта:

```sh
node ai/mock-server.mjs
```

Mock возвращает явно синтетические результаты и проверяет транспорт. Это не оценка Gemini.
Для реального сервиса ключ задаётся в терминале запуска (zsh):

```zsh
read -rs 'GEMINI_API_KEY?Ключ Gemini: '; echo
export GEMINI_API_KEY
export GEMINI_MODEL=gemini-3.5-flash-lite
node ai/gemini-server.mjs
```

Все точки запуска используют одну стандартную модель gemini-3.5-flash-lite. Сервер допускает
явный GEMINI_MODEL, проверочные T05/recheck фиксируют стандартную модель. Модель и версия
промпта сохраняются в метаданных. На Mac без node в PATH можно использовать
`"$HOME/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node"`.
Mock и Gemini запускаются на одном порту по отдельности. PORT/HOST переопределяются окружением;
по умолчанию 127.0.0.1:8001. Backend использует AI_BASE_URL. Для контейнера, обращающегося
к сервису на Mac, нужен доступный HOST и адрес host.docker.internal.

```sh
curl -sS -H 'Content-Type: application/json' --data-binary @ai/mock-request.json http://127.0.0.1:8001/v1/evaluations
```

## Правила оценки

Начальные критерии совпадают с официальным PDF. Сервис использует переданные description,
naCondition, scaleSteps и instructions, поддерживает RU/KZ/EN и произвольные ключи.
N/A не заменяет нехватку уверенности. Для выявления потребности уход клиента не означает,
что данных хватало; для консультации уход до формулировки запроса может разрешать N/A.

В версии 2.4.0 известные составные формулировки описаны декларативно в
config/check-policies.v1.json: контакт, выявление потребности, эмпатия, завершение и виды
грубых нарушений. Нужен полный набор отдельных проверок, а не одна общая положительная фраза.
Для завершения код объединяет (итог ИЛИ дальнейшая помощь) И прощание. Для эмпатии отсутствие
жалобы не считается нарушением условного требования. Для контакта положительная проверка
ссылается на первый ответ оператора. Для грубых ошибок проверяются все три вида отдельно.
В violations используется существующее строковое поле violation со стабильным ID из правил;
человекочитаемые названия подставляет код. Новые поля в responseJsonSchema для этого не добавлены.

Правила связываются с типом и нормализованным определением, а не ID диалога. Изменённый
критерий оценивается по текущей формулировке; чужие требования к нему не добавляются.
Произвольные новые формулировки разбивает на условия модель: код не доказывает её понимание
естественного языка. Известные эквиваленты можно добавлять в конфигурацию без правки кода.

Для применимого boolean=false checked_range обязателен независимо от omission и цитаты.
Проверка действует также в сравнении и экспорте. Для N/A нужны answer=null и непустой na_reason.
Отрицательный флаг требует проверки всего диалога. Шкала принимает обоснованную разрешённую
ступень; код не требует перечислять все отклонённые ступени. Вспомогательная ошибка review
даёт предупреждение, недостоверная цитата или неполные обязательные проверки отклоняются.

## Проверка без Gemini

```sh
node --test ai/*.test.mjs ai/evaluation/*.test.mjs
python3 -m unittest discover -s ai/evaluation -p 'test_*.py'
```

Тесты используют имитацию провайдера. CLI-регрессия проверяет полный локальный путь
HTTP 400 → private диагностика → сохранённая ошибка → отчёт → ненулевой exit code,
затем отсутствие повторного вызова при следующем запуске. Также проверяется запуск через
символическую ссылку, чтобы CLI не завершался молча без работы.

Скрипты run-once/recheck создают маркер ДО отправки, не повторяют начатую попытку и
останавливают пакет после GEMINI_REQUEST_REJECTED. Кэшированная ошибка тоже означает
неуспешный запуск. --dry-run не вызывает провайдера. Смена имени запуска — новая попытка,
требующая согласования квоты; она не является способом автоматического повтора.

Журнал сервера — JSON в stderr, без ключа, текста транскрипта и тела ответа Google.
События provider_dispatched / provider_headers / provider_body показывают наблюдаемые
этапы; dispatch не доказывает получение запроса Google. Таймаут 90 секунд, без повторов.
CLI сохраняет ответы провайдера и подробные ошибки только в private .run с правами 0600,
с удалением ключа. Для пакета файлы разделены по conversation_id и не перезаписывают друг друга.
Папки predictions-*, отчёты прогонов и логи исключены из Git.

## Интеграция и сдача

Исправление Жанель d6ca669 сохранено в истории, правило диапазонов e19c491 включено.
В версии 2.4.1 для известных условий Gemini возвращает ID в строке checks[].condition.
Для пользовательских формулировок в том же поле остаётся текст условия. AI проверяет
каждый обязательный ID, его группу, обоснование и ссылки на реплики до формирования ответа Backend.
Для p1-ru-025 со всеми восемью критериями responseJsonSchema структурно совпадает
со схемой успешного архивного запуска 2.3.0 (15aa6e9).
HTTP 400 всё ещё требует проверки реальным API: офлайн-тесты не подтверждают его устранение.
До согласования квоты реальный DEV/PROD запуск не выполняется.

У Backend есть независимые подтверждения N/A, привязанные к версии. Проверка фактического
N/A и следующей версии должна пройти вместе с Backend; её нельзя обойти подстановкой Нет.
Проверяйте реальный путь AI → Backend → score → сохранение → экспорт, затем изменённую версию
через интерфейс. Старые оценки и исходные данные сохраняются.

Рекомендуемый единый производитель официального results.json — Backend из сохранённых
оценок. AI-экспортёр остаётся офлайн-инструментом сверки; он не считает score. Его источники,
кодировка и индексы описаны в evaluation/SUBMISSION.md. Он проверяет isSuccess/total_records,
если они есть в исходной оболочке, и требует --overwrite для замены существующего output.
Нельзя маркировать mock как Gemini. Готовность 65 DEV и 10 полученных контрольных чатов
подтверждается фактическими оценками и push файлов до стоп-кода, а не зелёными mock-тестами.

в follow_up. Первый прогон и разметка остаются исходными материалами, не эталоном организаторов.
