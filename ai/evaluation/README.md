# Ручная разметка 12 DEV-чатов

Актуальная версия AI и правила запуска описаны в ../README.md. Разметка ниже —
исторический черновик. Название --run-name не выбирает версию промпта: выполняется
текущий код, а его версия и хеш фиксируются в manifest. Не используйте старые имена
попыток для проверки нового кода и не удаляйте маркеры ради повтора.

Если нужен результат уже завершённого запуска, та же команда прочитает архив и
покажет сравнение с первым прогоном. Например, для сохранённой версии 2.3.0:

```sh
node ai/evaluation/recheck-three.mjs --single-ru025 --run-name ru025-v2-3 --archive-only
```

При несовпадении manifest скрипт выводит версию и модель архива. Он читает полные
ответы или сохранённые ошибки для тех же диалогов и чек-листа, выводит сравнение в
терминал и сохраняет прежний файл отчёта. Неполный архив останавливает команду.
`--archive-only` разрешает только чтение, даже если папка отсутствует.

Без сетевых запросов текущий план можно проверить так:

```sh
node ai/evaluation/recheck-three.mjs --single-ru025 --run-name ru025-next-approved --dry-run
```

Реальный запуск требует отдельного согласования квоты. В версии 2.4.0 HTTP-ошибка или
кэшированный отказ дают ненулевой exit code. Подробности провайдера сохраняются приватно
в .run/provider-error.json (для одиночного прогона) или provider-error-ID.json (для пакета);
ключ редактируется, режим файла 0600. Сохранённые provider-response-ID.json не перезаписывают
друг друга. Сопоставление с разметкой не означает успешного получения оценок.

Черновая командная разметка после чтения всех выбранных транскриптов, по 4 RU/KZ/EN, всего 96 решений. Gemini для подготовки не вызывался. Это предварительные ответы для ревью, не эталон организаторов.

Основной файл — dev-12.manual.v1.json. В нём исходный снимок чек-листа, SHA-256 источника и каждого транскрипта, восемь решений на диалог, дословные цитаты, индексы от нуля и включительные границы checked_range. Имя и числовая шкала ответа соответствуют снимку чек-листа. Поля review и split относятся только к разметке, их не нужно отправлять в AI API.

Предложены 6 development и 6 holdout, по 2 на язык в каждой части. p1-ru-025 уже обсуждался в чате, поэтому это не полностью слепой контроль. Во время этой задачи разметка не использовалась для настройки промпта. Для слепой оценки следует позже отложить другие DEV-чаты.

Тестировщику нужно проверить все 96 решений. Для спорных мест сначала согласовать трактовку, затем внести принятый ответ, объяснение и review.status=approved. Наличие дословной цитаты подтверждает её происхождение, но не доказывает правильность оценки. Статистика по неподтверждённым меткам не должна называться точностью относительно официального эталона. Для KZ нужна дополнительная проверка человеком, уверенно читающим казахский.

База знаний недоступна. Некоторые пути меню подтверждены успехом клиента, но продуктовые факты не проверены по независимому источнику. Эти ограничения сохранены в JSON.

## Сравнение сохранённых ответов Gemini

Скрипт compare.py использует стандартную библиотеку Python 3. Он читает сохранённые HTTP-ответы и не вызывает модель. Подготовка отчёта не расходует квоту.

Сохраните ответы в папку ai/evaluation/predictions. Один файл — один исходный HTTP-ответ согласованного AI API. Название файла удобно задавать как p1-ru-001.json. В успешном ответе обязательны conversation_id, checklist_version и results. Для сохранённой HTTP-ошибки без conversation_id имя файла должно быть точным ID диалога. Также можно передать один JSON-файл с массивом HTTP-ответов.

Папка должна содержать только ответы для выбранных 12 диалогов. Ключи criterion_id должны быть строками "01"…"08". Для N/A используются answer=null, na=true и непустой na_reason. Исходный DEV-файл, его транскрипты и снимок рубрики проверяются по SHA-256. Версия в ответе должна соответствовать версии разметки; ID чек-листа может отличаться между установками Backend. HTTP-ответ не содержит полного снимка рубрики, поэтому совпадение его содержимого по одному ответу проверить невозможно: убедитесь, что сбор результатов использовал rubric.snapshot из разметки.

Из корня проекта:

```sh
python3 ai/evaluation/compare.py --predictions ai/evaluation/predictions --report ai/evaluation/report.json
```

Скрипт выводит отдельную строку для каждого критерия и список расхождений, сгруппированный по критериям. В JSON-отчёте сохранены все 96 сравнений, вопросы тестировщику и таблицы ожидаемый ответ → полученный ответ. Отдельные колонки показывают approved-метки, черновики без спорных и число спорных меток. После ревью approved имеет приоритет над прежним disputed=true.

Процент считается только среди валидных полученных ответов в соответствующей группе. Рядом всегда указано покрытие valid/expected. Пропуски, неправильная версия, таймауты, недопустимые ступени, повторные ключи и недостоверные цитаты помечаются unavailable, а не ошибочным смысловым решением. Отсутствующий checked_range при пропуске, указанном ручной разметкой, выводится как отдельная техническая проблема и не меняет совпадение answer. Произвольную смысловую правильность explanations и причины N/A нужно проверять вручную.

Пока все метки pending, approved-статистика будет пустой. Расхождения со спорными pending-метками видны в отчёте, но исключены из показателя совпадений. Совпадения с черновиком не являются точностью относительно эталона организаторов.

Проверка самого скрипта без вызовов Gemini:

```sh
python3 -m unittest discover -s ai/evaluation -p 'test_*.py' -v
```

Сохранённые ответы и отчёт локально исключены из Git через ai/evaluation/.gitignore.

## Однократный сбор ответов Gemini и сравнение

Из корня проекта в терминале с заданным GEMINI_API_KEY:

```sh
node ai/evaluation/run-once.mjs
```

На рабочем Mac без node в PATH:

```sh
"$HOME/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node" ai/evaluation/run-once.mjs
```

Остановить HTTP-сервис для этого не требуется: скрипт обращается к Gemini напрямую и порт 8001 не использует. По умолчанию модель gemini-3.5-flash-lite, её можно задать через GEMINI_MODEL до первого запуска. Скрипт отправляет выбранные 12 чатов последовательно, все восемь критериев одним вызовом на чат. Ответы и ошибки сохраняются в predictions/<conversation_id>.json. После сбора запускается compare.py и сохраняется report.json.

Для предварительного просмотра без ключа, сетевых вызовов и записи результатов:

```sh
node ai/evaluation/run-once.mjs --dry-run
```

В predictions/.run сохраняются manifest с моделью и хешами рубрики, разметки, исходника и evaluator, а также маркер попытки для каждого диалога. Маркер создаётся до вызова API. Повторный запуск пропускает сохранённые ответы и ошибки. Начатая, но прерванная попытка не отправляется заново, даже если ответ не успел записаться: вместо неё сохраняется ATTEMPT_INTERRUPTED. Автоматических повторов нет. Поэтому успешных результатов может оказаться меньше 12; отчёт покажет недоступные ответы отдельно.

При Ctrl+C или аварийной остановке может остаться predictions/.lock. Перед удалением только этой папки убедитесь, что прежний процесс завершён. Маркеры в .run удалять не следует: они предотвращают повторный расход квоты. Смена модели, промпта или разметки при том же manifest останавливает запуск. Если тестировщик исправил метки после сбора, запустите compare.py отдельно на сохранённых ответах, не запускайте новый сбор.

Это не гарантия exactly-once со стороны Google: при разрыве соединения невозможно узнать, был ли запрос обработан. Поведение клиента консервативное — не больше одной попытки отправки на диалог при сохранённых маркерах. Параллельный сбор в ту же папку блокируется.

Для проверки этой логики и всей офлайн-цепочки:

```sh
node --test ai/evaluation/run-once.test.mjs
```

## Анализ после уточнений организаторов

В отчёте теперь есть величина расхождения по исходной числовой шкале и число результатов в пределах одной ступени. Сравнение N/A с обычной оценкой помечается na_applicability и не включается в числовую среднюю ошибку. Соседние ступени и большие расхождения различаются как adjacent_scale и large_scale. Эти категории отражают расстояние по рубрике, а не автоматически установленную серьёзность ошибки: обоснования нужно читать.

Промпт 2.0.0 изменяет внутренний формат Gemini, но сохраняет внешний API. Старый manifest намеренно не позволяет запускать новый evaluator в ту же папку predictions. Старые ответы и маркеры попыток следует сохранить. Для просмотра старого прогона достаточно compare.py, который не обращается к модели. Новое измерение качества потребует отдельно согласованного прогона, а не автоматического повтора.

## Проверка трёх проблемных чатов после улучшения промпта

```sh
node ai/evaluation/recheck-three.mjs --dry-run
node ai/evaluation/recheck-three.mjs
```

Для живого запуска нужен GEMINI_API_KEY в этом терминале. Скрипт сохраняет новые ответы отдельно в predictions-recheck-v2, диагностику времени в predictions-recheck-v2/.run/diagnostics.log, отчёт с разметкой и изменениями по отношению к первому прогону в report-recheck-v2.json. Повторы запрещены теми же маркерами попыток, что у run-once; повторный запуск не отправит уже начатые чаты. Ошибки также сохраняются.

Для повторного чтения готовых результатов без ключа и сетевых обращений:

```sh
python3 ai/evaluation/compare.py --predictions ai/evaluation/predictions-recheck-v2 --ids p1-ru-025,p1-en-015,p1-en-014 --baseline ai/evaluation/predictions --report ai/evaluation/report-recheck-v2.json
```

Отчёт содержит 24 решения и поля before/after с обоснованиями. Автоматическая смена ответа ещё не означает улучшения: нужно проверить факты и спорные метки вместе с тестировщиком.

В целевом прогоне трёх чатов отклонение запроса Google (GEMINI_REQUEST_REJECTED) теперь останавливает отправку остальных чатов. Это позволяет сначала исправить общий формат запроса, не отправляя заведомо похожие запросы дальше. В уже выполненном первом целевом прогоне все три HTTP 400 сохранены; они не удаляются и автоматически не повторяются.

Для отдельной проверки p1-ru-025 на компактной схеме предусмотрен флаг --single-ru025. Он отправляет только этот чат со всеми восемью критериями на gemini-3.5-flash-lite, сохраняет попытку в predictions-ru025-schema-check и сравнение с первым прогоном в report-ru025-schema-check.json. Повторный запуск пропускает уже начатую попытку. Ключ должен быть задан в терминале запуска.

```sh

```

## BUG-004 — доказательства и диапазон

Правило compare.py совпадает с Backend: при непустом checked_range индекс КАЖДОЙ цитаты должен попадать в диапазон start <= turnIndex <= end. Границы включительны. При checked_range=null проверяются сам индекс и дословность цитаты без дополнительного ограничения диапазоном.

Достоверная цитата из реплики 1 при диапазоне [0, 0] теперь даёт unavailable с причиной evidence вне checked_range и не входит в matches или valid. При диапазоне [1, 1] та же цитата проходит. Это техническая ошибка доказательства, а не смысловое расхождение с разметкой.

В черновой ручной разметке расширены четыре диапазона, чтобы они включали уже выбранные контекстные цитаты: p1-ru-009/05 до [0,15], p1-ru-022/02 до [0,11], p1-en-008/04 до [10,18], p1-en-015/02 до [0,10]. Ответы, цитаты, объяснения и статусы ревью сохранены. Это меняет хеш файла разметки, поэтому существующий manifest сбора намеренно остановит новый запуск; офлайн-сравнение сохранённых ответов работает без повторных вызовов Gemini.

## T05: идентификация при вопросе о публичных тарифах

В t05-request.json сохранён отдельный синтетический диалог из двух коротких реплик и только критерий c3 (идентификация). Тип boolean, allowNa=true, naCondition — запрос не требовал идентификации. Вес изолированного критерия 100 нужен только для целостности тестового чек-листа; баллы в этой проверке не рассчитываются.

Запуск из терминала с GEMINI_API_KEY:

```sh
node ai/evaluation/t05-once.mjs
```

Модель фиксирована: gemini-3.5-flash-lite. Ожидание — answer=null, na=true, непустой na_reason. Результат сохраняется в predictions-t05-na-v2-1/T05.json; диагностический журнал — в .run/diagnostics.log внутри этой папки. При HTTP 200 сохраняется также исходное тело ответа Google в .run/provider-response.json, чтобы ошибку валидации можно было разобрать офлайн. Ключ и заголовки авторизации не сохраняются. В .run/verification.json находится PASS/FAIL/ERROR с версиями и итогом попытки.

Повторных запросов нет: до вызова создаётся маркер, успешный ответ и ошибка кэшируются одинаково. --dry-run только показывает план. Тесты с имитацией ответов: node --test ai/evaluation/t05-once.test.mjs.

Команда также готовит HTML-страницу прослушивания звонков с перемоткой вперёд/назад. Для LLM-модуля это средство проверки оснований оценки по записи: исходные временные метки и ссылки на реплики нужно сохранять для перехода к нужному фрагменту. Реализация интерфейса остаётся задачей участника Frontend.
