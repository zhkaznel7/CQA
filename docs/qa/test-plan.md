# План проверки SQA · CQA Hackathon

Ответственный за прогон — Жанполат, участник №4. Цель — проверить путь от импорта диалога до оценки с доказательствами и сохранённого решения по апелляции.

## Основание и данные

Номера T01–T16 и ожидаемое поведение взяты из обсуждения команды. Оригиналы требований CQA Hackathon, Chat Quality Checklist и расширенного плана в этой папке отсутствуют. Перед приёмкой сверить шкалы, условия N/A и контрольный расчёт с версией чек-листа команды. Приоритеты в журнале предложены для первого прогона.

Для прогона нужны тестовый экземпляр приложения, DEV с перечнем ID, тестовый звонок с аудио и транскриптом, роли заявителя и проверяющего и версия чек-листа. Для пограничных ситуаций использовать искусственные диалоги. Разметку ожидаемых оценок подготовить до запуска модели. Для T04 и T12 отдельно записать ручной расчёт по той же версии чек-листа.

## Порядок прогона

1. Зафиксировать дату, версию сборки и чек-листа. Работать в тестовой группе. Для T15 использовать экземпляр, который можно перезапускать.
2. Выполнить [сценарии](test-cases.md). P1 проверяет достоверность результата или сохранность данных. P2 покрывает остальные функции командной матрицы. Оба приоритета входят в прогон.
3. Указать в строке результат и ссылку на подтверждение с ID диалога или оценки. «Пройден» означает, что наблюдались все ожидаемые результаты. При расхождении поставить «Ошибка» и завести запись в [журнале дефектов](defects.md). Если нет зависимости, указать «Заблокирован» и чего именно не хватает.
4. После исправления повторить сценарий на указанной сборке. Для изменений пересчёта повторить T04, T12 и T13. Итог прогона включает число проверок в каждом статусе и открытые дефекты.
